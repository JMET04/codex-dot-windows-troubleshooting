# 实际案例：2026-10-10

## 环境

- Windows 上的桌面应用，本机电脑显示 connected、attached、已授权。
- 日志记录桌面版本 26.1002.7124.0。
- 使用的内置 CLI：0.162.0-alpha.2；Python 3.12.14。
- 上述为本案例版本，不能据此证明其它版本都受影响或都已修复。

## 症状分成三类

**本机初始化失败**：Dot 委派执行任务时，进程尚未创建，返回 helper_unknown_error / setup refresh had errors。沙盒日志具体指向 node_repl.exe 的运行库权限刷新和 Windows error 32。

**云端与旧本机聊天访问不兼容**：Dot 主会话的 cloud_threads_read 返回 unsupported placement format version 1；云端发送本机目标返回 NOT_FOUND。另一个旧活动聊天无法加载，桌面日志同时有 durable WebSocket 403。这些错误的共同原因没有确认，不把它们和文件共享冲突混为一谈。

**请求超时与实际执行不同步**：启动继续请求返回 UNKNOWN / TimeoutError，起初只能读取旧回合；随后原测试任务实际运行完成、写出成功结果。这说明“未得到接收确认”不能改写成“确定没执行”。

## 原因与修复

原配置使用 elevated。日志显示运行库权限刷新在打开正在使用的执行文件时失败。官方 PR #51822 描述了同类文件共享冲突，并已于 2026-10-07 合并。

将已有 [windows] sandbox 选择改为 unelevated 后，本机启动恢复，Dot 生成了真实文件往返回件。此配置是官方支持的旧版次级备用实现，并有隔离能力限制；它没有修复云端目标格式错误。不能宣称正式桌面更新已安装相关源码修复。

释放本次读屏控制会话、暂时停止读屏等先前尝试没有解决初始化失败；本案例没有通过结束其它程序或广泛修改 ACL 解决。

## 控制测试的关键过程

在一个用户明确授权的原技能聊天中，只允许发送单条校验码消息，不调用工具、不修改项目、不恢复定时任务。

最初的本地审查包装器未允许新增的 thread/turns/list，在发送前停止，实际发送次数为零。它是本地方法清单未同步，**不是平台自动审批拒绝**。随后固定脚本及清单，增加实际桌面空闲检查、最新回合复查和独占预约文件。

启动调用之后发生超时；检查本地结果与目标实际聊天才发现它已最终成功。目标真实回合完成，准确返回相同校验码。发送方结果和独立桌面读取的回合编号一致。Dot 主会话也通过正式读取重新核对了原测试任务的成功结果。
