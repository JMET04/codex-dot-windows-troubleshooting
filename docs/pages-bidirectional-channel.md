# Dot 与本地项目的私人 Pages 通讯

> 此方案已停止。用户最新明确要求官方原生直连，排除定时收件、本地控制台和屏幕消息中继。官方删除接口返回任务不存在，实际自动化配置文件也不存在。下文是历史实验记录，不能据此恢复部署或派发遗留请求。当前范围见 [原生直连验收](native-direct-connection.md)。

2026-10-12 实测完成一次私人 Pages 往返：Dot 自己写出新请求，本地官方桌面接口将它转交给一个已授权的原项目；项目读取同一 Page、核对请求并亲自写回回执；Dot 读取回执后写确认。页面预览实际显示三段 JSON，原挑战与回执一致，项目生成的返回挑战与 Dot 确认一致。

这提供了已验证的数据交换路径。第一次转交及通知由正在检修的聊天完成。后续部署的每分钟收件任务在独立本地控制台实际读到另一条新请求、向原项目转交一次，项目自己保存新回执，Dot 自己写确认，收件器正式读回三段匹配，序列为 6。一次自动挑战往返已经通过；普通项目指令仍在启用和验收，不能据此宣称长期无人值守稳定或原生电脑连接已修复。

## 如何建立

1. 分别核对 Dot 和本地项目本轮真正暴露的 Pages 工具，实际调用一次只读操作验证访问。工具名出现在目录中，不代表当前进程可以调用。
2. 创建同账号的私人 Page，分开保存请求、项目回执和发送方确认。保留 Page 原始 ID；不要改分享设置。
3. Dot 生成唯一请求编号和随机挑战。本地转交者从 Page 读取，检查目标授权、当前是否空闲，并先以独占创建方式保留一次发送记录。这里只允许独立的 `reply_only` 测试。
4. 使用当前桌面正式聊天接口转交一次。等待该目标的真实新回合完成，并核对准确的请求编号与挑战。
5. 项目自己读取 Page 并写回回执，附带自己生成的返回挑战和实际执行回合。使用当前读取的 block ID 与 hash 保存，随后读回核对。
6. Dot 从同一 Page 读回并写确认。核对三个持久化记录，不能把“已读”、工具暴露或聊天中的成功说明单独当作验收依据。

## 实测范围

| 环节 | 结果 |
| --- | --- |
| Dot 写请求并读回 | 成功 |
| 本地检修聊天读取新请求 | 成功 |
| 官方桌面接口转交到原项目 | 一个新回合完成，实际 JSON 回复匹配 |
| 原项目读取同页并写回回执 | 官方 read_page 两次，edit_page 一次；保存序列 2 |
| Dot 读取回执并写确认 | Dot 报告保存与读回成功，序列 3 |
| 三段持久化内容 | 页面预览实际加载，挑战和返回挑战均一致 |
| 此后独立 API 读取确认 | 首次发生网络错误；后续正式读取成功，三段 JSON 完全一致 |
| 自动收件、唤醒空闲项目 | 已部署；独立定时回合实际读到新请求并转交一次 |
| 新自动请求的项目回执 | 原项目回合完成，自己保存并读回；收件器独立读回匹配，序列 5 |
| 新自动请求的月儿确认 | 收件器从页面实际读到新 ACK，返回挑战匹配，序列 6 |
| 新自动往返 | 挑战测试通过；项目发送 1 次，收件器 UI 通知发送 0 次 |
| 原生电脑执行路径 | 没有恢复证据，仍有新的云端 HTTP 403 |

后续正式读取分别确认了第一次人工转交往返和另一条自动挑战往返，但未消除此前的访问错误。请求必须持久化，网络错误后先对账；发送结果不明时不得自动重复派发。单次挑战测试不覆盖普通业务执行、繁忙排队或长期稳定性。

## 自动收件为何没有启动

最初的每分钟 heartbeat 指向仍在持续运行的检修聊天。只读检查实际调度数据库发现 `last_run_at` 为空、`next_run_at` 持续向后推进；原项目没有新回合，新的页面请求仍为 pending。安装版调度代码会核对目标的 renderer 和回合状态；这些观察与目标忙碌时延期运行一致，未取得足以区分具体延期分支的日志。ACTIVE 配置本身不能证明收件已经执行。

通过正式 automation_update 更新同一个任务，使其指向用户已授权创建的独立本地控制台，保留原请求和防重记录。随后实际 `last_run_at` 更新，控制台记录出现带 heartbeat 触发正文的新回合，Pages read_page 调用成功，正式聊天发送接口转交一次，原项目出现对应的新回合。没有新建额外聊天、重启应用或重发旧请求。

发送后的本地记录更新还遇到一个 PowerShell 错误：`File.Replace` 的空备份参数被转换为空路径，而 PowerShell 未因此返回非零退出码。控制台随后修正记录并读回 `send_attempts=1`。命令退出码与输出中的“成功”字样不足以确认写入；必须核对实际持久化记录。新请求已预约后，即使记录更新失败，也不得重新发送。

新的原项目回合后来完成，项目自己通过官方接口保存并读回回执，序列为 5；独立定时收件回合也再次读取页面并核对了请求、挑战及真实回合。返回通知使用正式原生 Computer Use，第一次导航遇到其他窗口覆盖，没有发送消息，也没有重派项目请求。之后另一个真实定时回合正式读到 Dot 写入的新 ACK，返回挑战完全一致，序列为 6。确认到达前没有发送收件器 UI 通知，三段匹配记录已保存在本机。

普通 `project_message` 和只读 `thread_status` 的规则、格式及本机项目索引随后已经通过正式接口保存并读回，序列为 7。索引来自本轮正式工具结果：29 个本机项目、8 个返回的已有项目聊天。没有返回聊天的项目不会自动新建或猜测目标，派发前还需核对准确目标及其空闲状态。单请求在确认前保留，发送未知时只对账。普通指令的真实本机执行、结果返回以及繁忙排队仍在验收，不能用挑战测试代替。

新的业务通知随后只发送一次，Dot 实际提交了新的项目请求。独立定时收件回合正式读到序列 8，核对现有本机项目和空闲状态后独占预约并转交一次。真实业务回合最终 `failed`，错误为 `Selected model is at capacity. Please try a different model.`，实际仅成功读取技能说明；窗口计数、目标命令和业务文件尚未完成。目标实际权限为完全访问、审批模式为 `never`，这次失败不能归因于本机文件权限。已有发送预约保留，没有重派旧业务。

Codex 内置页面编辑器另能读取完整的新请求；富文本界面显示的 Windows 路径反斜杠与原始 Markdown 不同，按可见文本转录后的全部字段与后来的正式序列 8 读取完全一致。这个对照是只读界面备用路径的证据，尚不代表独立收件器自动使用该路径通过验收。工作流已加入来源区分、完整性核对和同一防重账本。

容量失败通过一个新的、仅做失败对账的协调回合尝试备用模型。该回合不得重复原业务操作；失败回执必须由原项目自己核对并生成。月儿确认失败与下一条使用新编号的新业务验收分别记录，不能把诚实失败回传当作电脑控制成功。

后续备用模型协调回合虽显示 `completed`，最终却只返回历史测试文本，没有处理新的对账指令。实际记录表明该次任务通过工具输出转交；尚不能据此断定错误的具体原因。收件器没有把这次完成状态当作模型恢复，也没有重派原业务。

随后使用同一原项目的官方输入框只发送一次新的明示协调。正式聊天记录核对了新 `userMessage` 与完整协调指令精确一致，实际新回合也明确回应当前失败对账任务。该回合自己读取聊天记录成功，Pages 读取实际失败；随后长时间未结束，检修在没有活跃工具时停止了这条自己发起的只读对账，正式状态为 interrupted，没有重派业务。

新的收件规则为这个原项目准备了输入框转交路径：仅在当前对账和旧失败确认真正核对后，才处理下一条未预约的新编号；输入和发送分别预留，发送结果未知只对账，正式核对准确新用户消息及实际任务结果。其他目标保留现有工具路径。这是有条件的路径调整，不能把已进入输入框或正在处理当作业务控制恢复。

项目接口联网失败后，进一步准备了用户已经授权的本地文件与屏幕回传路径。原项目自己生成失败回执和返回挑战，收件器正式核对实际回合、原文件与 SHA256，再一次经原月儿输入框传递原文；月儿作为明确披露的中继发布并确认。这条返回路径尚在验收，不能冒充项目自己通过 Pages 发布成功。

新的本地回执协调已只发送一次，正式新用户消息与完整指令精确一致。实际模型为 gpt-6-luna/low，审批为 never、完全访问；项目已明确响应当前任务并读取历史回合，仍等待它自己保存文件和匹配最终回复。没有执行旧业务，也没有取得新的普通业务往返证据。

## 当前网络复核与原子替换

新的只读检查中，两个固定域名在无显式代理和现有回环代理路径上均通过严格 TLS 验证，但同一时段的桌面日志仍有近期原生云端 HTTP 403。因此旧证书故障不能解释当前全部问题，TLS 通过也不能证明电脑控制已经恢复。匿名公共根页面的应用请求未证明登录端点或电脑执行能力；没有保存响应正文、headers 或凭据。

PowerShell 的空参数转换错误还影响到先前未实际改 hosts 的有界测试助手：`File.Replace(..., $null)` 会被绑定为空路径。新临时文件回归实测先复现错误，再用 `[System.Management.Automation.Language.NullString]::Value` 验证替换与还原。新助手副本已修正，限制最长 60 秒，保留旧文件；仅做只读预检，系统 hosts 没有改动。本机收件记录使用正确原子替换，并强制读取持久化结果。

后续同日的系统代理路径又出现证书名称不匹配，直接路径仍通过严格 TLS。使用本机解析地址的代理对照结果包含成功和超时，不能据此断定全部故障仅由 DNS 导致。一条已有保存线路在独立、只允许两个固定诊断域名的回环测试中通过严格 TLS；测试进程已退出，临时配置已删除，原代理配置未改。这些诊断不证明登录请求、原生云端连接或业务执行恢复。

## 代理诊断

隔离 CLI 在一个已授权、空闲的本地控制台临时启用 `respect_system_proxy`，没有修改全局配置。工具目录中虽有 Pages 名称，实际调用返回工具不可用，未读取页面；此次诊断不能证明该选项是否修复联网。

另一项隔离试验使用用户已经安装的 FlClash Core 和已有节点，关闭 TUN、DNS 与控制器，只开放回环代理，并仅允许两个固定域名。初始化、配置校验和监听启动成功，但两个目标的 TLS 校验均以 `SSLEOFError` 失败。自建进程已经退出，临时节点配置已移除，原偏好设置与原配置逐字节未变。没有修改系统代理或 hosts。

`scripts/isolated_proxy_config.py` 只构造这类隔离配置，不启动代理，不更改系统设置，也不提供上游节点。六项合成测试覆盖监听范围、禁用系统捕获、域名范围、深复制及无效输入；测试通过不代表真实节点可用。

原始 Page、请求、聊天 ID、挑战字串和网络配置保留在用户本机，没有收入此仓库。
