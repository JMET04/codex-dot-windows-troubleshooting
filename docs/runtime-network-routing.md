# 保留登录和任务的运行中连接排查

记录日期：2026-10-11。本轮没有恢复 Dot 的云端连接；下面是新增证据和修复范围，不能把诊断进展当作修复完成。

后续严格 TLS 对照发现网页域名的代理证书错配，以及无显式代理仍经过现有 WARP。临时路径试验未恢复连接，试验配置均已回滚；详见 [网页 TLS 与隧道实测](tls-and-tunnel-routing.md)。它不改变以下历史匿名请求记录，也没有证明后台 403 的原因。

## 匿名 HTTP 对照

使用当前已配置的本机代理与不显式指定代理两种路径，分别对公开服务根路径发出有超时限制的匿名请求。没有读取或传输登录凭据、浏览器会话或聊天内容，没有改变网络设置。

| 服务 | 方法 | 请求路径 | 结果 |
| --- | --- | --- | --- |
| codex-cloud-backend.chatgpt.com | HEAD | 已配置代理 | 403，Cloudflare challenge 标记 |
| codex-cloud-backend.chatgpt.com | GET | 已配置代理 | 401，没有 challenge 标记 |
| codex-cloud-backend.chatgpt.com | HEAD / GET | 无显式代理 | 403，没有 challenge 标记 |
| chatgpt.com | GET | 已配置代理 | 403，Cloudflare challenge 标记 |
| api.openai.com | GET | 无显式代理 | 403，unsupported-region 标记 |

另一次匿名 GET 加入标准 WebSocket Upgrade 请求头：已配置代理路径返回 401，无显式代理路径返回 403，均无 challenge 标记。没有发送认证协议或凭据；这仍不是桌面真实会话的 WebSocket 验收。

不同方法、服务和路径的结果不同，不能把 HEAD 的 challenge 直接归因到桌面 WebSocket。401 只表示该匿名请求获得了 HTTP 响应，不证明登录后的连接会成功。“无显式代理”也不证明操作系统或上游没有其他网络转发。以上检查不是切换路由或绕过验证的方案。

## 安装版的连接路径

只读检查 Windows 安装包 26.1007.2314.0 的静态代码：durable 主机使用公开云端 WebSocket 地址；其连接工厂对该主机不选择显式 SOCKS 代理，随后构造 Node WebSocket。检查到的主文件中没有 Windows 系统代理解析调用。内部主机使用 SOCKS 的另一分支不适用于该公开主机。

这支持“桌面云端 WebSocket 与采用系统代理的页面请求可能走不同路径”的假设。它没有证明运行时最终出口、具体请求的代理使用、账户会话是否有效或服务端为什么拒绝。未修改安装包，也没有挂接运行中的进程或自行搬运认证头。

同一时段桌面日志仍记录云端握手 403、ready 前失败。页面显示电脑“已连接”并不足以证明云端执行可用；需要新的成功握手、Dot 实际工作任务和准确回执分别验证。本轮没有发送新测试，也没有重发已有中断请求。

## 本轮采用的检修方式

保留当前登录和运行中的用户任务。已有会话刷新请求观察超时后不重复，更新检查超时也不记为最新版。继续使用本机正式只读接口核对状态，保留经过过滤的启动错误和失败回执。

目前没有验证出可在应用运行中为此公开云端 WebSocket 设置代理的受支持入口。因此未把猜测的环境变量、命令沙盒网络配置、全局路由改变或重启当作已验证修复。官方配置说明明确区分命令网络代理与原生应用、MCP 等其他流量；不能把命令代理配置当作桌面云端连接设置。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

可供官方或网络管理者核对的材料是：安装版本、握手失败时间、公开主机、匿名请求的方法及状态、静态连接路径摘要。原始日志、设备标识和配置备份保留本地；公开脱敏摘要见 [network-routing.redacted.json](../evidence/network-routing.redacted.json)。

验收仍要求：在线通道成功连接，Dot 自己读取实际失败回执，以及新的授权任务得到完整回复。已经保存的电脑授权和本机终端成功记录，不能代替这些结果。[Dot 电脑与应用连接](https://learn.chatgpt.com/docs/dots/computers-and-apps)。

## 与公开问题的关系

查询时，官方 GitHub 仓库的 [问题 #49458](https://github.com/openai/codex/issues/49458) 仍为 open，记录了其他 Windows 用户的 Dot 任务缺少 Computer Use 工具的现象。这是用户提交的问题记录，不是官方确认的根因或修复公告。工具缺失与本案例当前云端握手 403 必须分别验收，不能仅凭相似症状认定同一缺陷，也不能据此声称某个更新已经解决。

## 运行中页面与日志核对

2026-10-11 在保留登录和任务的情况下，通过桌面屏幕读取实际设置：常规中的“完整访问权限”、连接中的“允许连接”、电脑操控中的“任意应用”均已开启。没有改变这些开关，也没有撤销电脑授权。

Dot 电脑选项中看到了选择当前电脑和撤销访问权限；检查的设置页面没有找到专门针对 durable 云端通道、同时保留当前登录的重连入口。“云电脑”页面管理网站 Cookie，连接页面管理设备远程控制，Codex 云端页面管理项目环境；不能把这些不同入口当作同一通道。没有执行聊天菜单中的重启操作。

导航期间页面出现“恢复对话失败 / Codex app-server is not available”。同一时段日志记录云端 WebSocket 在 ready 前返回 403，随后的云端线程读取和恢复请求以 `remote_unavailable` 失败。应用已有自动重连持续运行，每次观察到的重连仍返回 403。这些证据指向当前云端传输不可用；具体服务端拒绝原因仍未查明，不能据此要求重开电脑权限或声称重启可以根治。

新增 [inspect_cloud_connection.py](../scripts/inspect_cloud_connection.py) 可在应用运行时读取有上限的日志尾部，不连接服务或启动 app-server。仅识别已知日志来源的 durable 事件，忽略本机事件；按事件时间取最新状态，过期记录明确标为 stale，新 ready 不会被旧 403 覆盖。与不可用错误的时间相关计数不等于证明服务端拒绝原因，也不等于连接尝试次数。

该工具在本机当前日志中返回 `cloud_websocket_http_403`。测试覆盖来源区分、凭据和标识不进入报告、新旧事件顺序、未来时间、读取上限及拒绝覆盖既有证据；全仓 14 项测试通过。脱敏核对见 [desktop-ui-state.redacted.json](../evidence/desktop-ui-state.redacted.json)。这些通过只证明诊断行为，原生控制尚未通过。
